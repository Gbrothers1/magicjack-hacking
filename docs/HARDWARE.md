# Hardware reference — magicJack units studied

This repo has been run against **two different generations** of the magicJack USB hardware. Both
enumerate as the same USB device (`06e6:c200`), but their chips and control registers differ, so tools
written for one can fail on the other.

| | **Unit A — magicJack HOME** (ARM) | **Unit B — magicJack A921** (legacy / non-ARM) |
|---|---|---|
| `bcdDevice` | `0.08` | `0.01` |
| DevType ([how](#identify-your-generation)) | 8 (ARM) | 1 (non-ARM) |
| HID vendor feature report | **64** bytes | **32** bytes |
| HID report descriptor length | 111 bytes | 133 bytes |
| Chip-revision reg `0x55` | `0x12`/`0x13` (read-only) | `0x13` |
| Hook state | `reg0x14` bit 31 | register byte `0x12` bit 5 (= `reg0x10` bit 21) |
| DTMF | `reg0x14` bits 24–27, valid bit 16 | byte `0x15` bits 0–3, strobe bit 6 (see *DTMF timing (Unit B)*) |
| Line power | `reg0 \|= 1`, `reg0x38 = 3` (verified: dial tone + LED) | same writes accepted; keypad sidetone heard (see *Line power (Unit B)*) |
| Ring | `reg0 \|= 0x300` (verified) | **not found** — those bits don't latch |
| ProSLIC via SPI bridge (TJ regs `0x26–0x29`) | firmware blocks it (stalls) | transfers complete but the SLIC never answers (`0xff`) |
| Dial tone | generated by firmware at off-hook | not from `line_on()` alone (see *Audio behaviour (Unit B)*) |

Everything known about each unit is grouped and tagged by confidence:

- **[verified]** — observed directly on the device (via `lsusb`, `/proc/asound`, `dmesg`, firmware
  memory, register dumps, or physical behavior with a real phone attached).
- **[reported]** — the device's own firmware / ZeroCD self-report (may not match the physical model).
- **[inferred]** — deduced from the evidence or from vendor-binary analysis, not directly tested.
- **[unverified]** — could not be confirmed; read it off your own unit to be sure.

## Identify your generation

Run these before trusting any register tool in this repo.

```bash
lsusb -v -d 06e6:c200 2>/dev/null | grep -E 'bcdDevice|wDescriptorLength'
# feature-report size straight from the HID descriptor (no root needed):
for h in /sys/class/hidraw/hidraw*; do grep -q 06E6 $h/device/uevent && xxd $h/device/report_descriptor | tail -2; done
```

- **`bcdDevice` → DevType:** `table[(bcdDevice & 0xF) − 1]` with `table = [1,2,0,4,5,0,7,8]` (from the macOS
  updater, see `captures/mac-binary-ARM-protocol.md`). ARM iff DevType ∈ {5, 7, 8}. `0.08` → 8 (ARM);
  `0.01` → 1 (non-ARM). **[inferred]**
- **Feature-report size** is the last `95 NN b1 00` in the HID report descriptor: `95 40` = 64 bytes (ARM),
  `95 20` = 32 bytes (legacy). Sending a 64-byte report to a 32-byte unit makes the device **STALL**, which
  Linux reports as `BrokenPipeError: [Errno 32]` — the symptom that revealed Unit B. `tj_linepower.py` now
  reads this size itself. **[verified]**
- **Chip probe** (as the Windows driver does): `reg 0x01 & 0x6C == 0x6C`, then `reg 0x55`: `0x13` → "type 2",
  `0x12` → "type 3" (see `protocol.md`). Unit B reads `0x01 = 0x6c`, `0x55 = 0x13`. **[verified]**

> **The name discrepancy is itself a finding.** The physical unit is a **magicJack HOME**, but its
> firmware banner and ZeroCD volume still self-identify as **`magicJackPlus`** — because the HOME is
> built on the **same YMAX / TigerJet platform** as the magicJack Plus. Treat the `Plus` strings below
> as *observed platform strings*, not the product name.

For a real photo of the device, see magicJack's official product page:
<https://www.magicjack.com/> (link only — no vendor image is redistributed in this repo). The
illustration in [`magicjack.svg`](magicjack.svg) is an original drawing.

# Unit A — magicJack HOME (Home Edition, ARM)

> The sections from here to the Unit B heading describe the **HOME** the project was originally built on.

## Physical  **[verified from photos + behavior]**

- **magicJack HOME** — a small **black enclosure with a blue accent stripe** around it.
- **Front ports:** an **RJ45 Ethernet** jack and an **RJ11 telephone** jack (phone icon), side by side.
- **Status LEDs:** two small indicators (green / amber) on the front.
- **USB:** a **USB-A** connector for plugging into a PC.
- **Power:** DC power for standalone use.
- **Two ways to run it:**
  1. **Standalone** — Ethernet + power; the on-board networked brain runs SIP to magicJack's cloud.
  2. **Over USB** — plugged into a PC; magicJack's app (or, here, our Linux tooling) drives the
     attached phone through the USB front-end. **This project uses the USB path.**

---

## USB identity  **[verified — `lsusb` / kernel enumeration]**

| Field | Value |
|---|---|
| VID:PID | `06e6:c200` — Tiger Jet Network, Inc., "USB Internet Phone by TigerJet" |
| iSerial | `<device-serial>` (USB hardware serial — **not** the SIP account id) |
| bcdDevice | `0.08` |
| USB | 1.1 full-speed, bus-powered (~500 mA) |

**Five interfaces:**

| # | Class | Linux node | Role |
|---|---|---|---|
| 0 | Mass Storage | `sr0` | ZeroCD autorun installer stub |
| 1 | Audio Control | card mixer | mute/volume |
| 2 | Audio Streaming (capture) | ALSA card | line → host, 8 kHz mono |
| 3 | Audio Streaming (playback) | ALSA card | host → line, 8/16 kHz mono |
| 4 | HID (Telephony) | `hidraw` | hook/DTMF input + 64-byte vendor control report (all chip control) |

Full descriptors: [`../06-magicjack-usb-tigerjet/captures/usb-descriptors.txt`](../06-magicjack-usb-tigerjet/captures/usb-descriptors.txt).

---

## Chips  **[verified — firmware strings + behavior]**

- **TigerJet USB controller**, family **TJ780 / TJ880**, **ARM-based** SoC — carries the ARM firmware
  that owns the line. (DevType 8 = the ARM/flash-capable variant; see the ARM protocol notes.)
- **Silicon Labs Si321x ProSLIC** — the analog line / **FXS** chip: powers the loop, generates the
  ring voltage, and detects hook + DTMF on-chip. On this ARM platform it is driven by the TigerJet's
  **on-chip firmware**, not directly by the host.
- **On-board SPI flash** — holds the TigerJet firmware.

Datasheets (background reference, fair use): [`../06-magicjack-usb-tigerjet/datasheets/`](../06-magicjack-usb-tigerjet/datasheets/)
(`Si3210-ProSLIC.pdf`, `Tiger560B.pdf`).

---

## Firmware  **[reported — device self-report]**

- **Firmware banner:** `Version 19.20 (magicJack 560/580/780/880/980/911)`; board `IPC11`.
- **ZeroCD volume label:** `YMaxCorp magicJackPlus CD 3.00`.
- The platform **self-identifies as `magicJackPlus`** even though the physical unit is a HOME (same
  YMAX/TigerJet platform — see the note at the top).

## SIP identity  **[verified in packet capture]**

The **networked brain** (Ethernet, the ATA/SoC — a separate computer from the USB front-end) registers
to magicJack's cloud as:

- `sip:EXXXXXXXXXXXX@talk4free.com` — **placeholder**; the real serial-like username is redacted in
  this public repo.
- **No authentication** (empty password unless challenged), **G.711** audio.

This is what makes the self-hosting hack possible — a matching Asterisk endpoint captures the
registration. Details: [`../02-cisco-1841/magicjack-sip-notes.md`](../02-cisco-1841/magicjack-sip-notes.md)
and [`../03-magicjack-sip/`](../03-magicjack-sip/). Note the SIP username lives in the ATA brain's DRAM
and is **separate** from the USB hardware serial `<device-serial>`.

## Model number / FCC ID  **[unverified]**

Not confirmed for this HOME unit. Earlier notes assumed a Plus (`K1103` / `Y79K1103`), which is **not
verified** here. **Read the model number and FCC ID off the label on your own device** to identify it
precisely — then look the FCC ID up at <https://fcc.report/> or the FCC OET database.

# Unit B — magicJack A921 (legacy / non-ARM, `bcdDevice 0.01`)

A USB-only adapter with an RJ11/RJ13 phone jack, made for North American phones. Findings below come from
tests on one unit (its iSerial begins `A921…`; the rest is redacted as `<device-serial>`), driven from Linux
with the tools in `06-magicjack-usb-tigerjet/tools/` and `03-magicjack-sip/mj-audio.py`. This is a working
map, not a full reverse-engineering of this generation.

## USB identity (Unit B)  **[verified — `lsusb -v`, `dmesg`]**

| Field | Value |
|---|---|
| VID:PID | `06e6:c200` — same as Unit A |
| bcdDevice | `0.01` |
| USB | 1.1 full-speed, bus-powered, `MaxPower 500mA`, 5 interfaces, 1 configuration |
| HID | interface 4, bound by `hid-generic` → `hidraw` **and** `hiddev`; report descriptor **133 bytes**; interrupt IN `0x85`, **8-byte** packets, 10 ms interval |
| Mass storage | two LUNs: `TigerJet HardDisk v2.0` (~18.6 MB, FAT, write-protect off) and `TigerJet CD-ROM v2.0` (ISO 9660 + Joliet). Auto-mounts on plug-in; unmount/eject if it gets in the way. |

Interfaces 0–3 match Unit A (mass storage, audio control, capture, playback). Audio terminals are `Handset`
(`0x0401`) and `USB Streaming`; both feature units expose **Mute + Volume**.

## HID report descriptor (Unit B)  **[verified — read from sysfs]**

Read it with `xxd /sys/class/hidraw/hidrawN/device/report_descriptor` (no root). Summary:

- **Input** (Telephony page `0x0B`): keypad usages `0xB0–0xBB` (4-bit), hook-switch usage `0x20` (1-bit),
  assorted phone-button usages and a Consumer volume usage. These are the events the Windows driver reads from
  the interrupt endpoint; **this repo's tools do not use them** (see [leads](#open-questions--leads)).
- **Feature** (vendor page `0xFFFF`): one report, **32 bytes** (Unit A: 64). All chip control goes through it.

## Chips (Unit B)  **[inferred]**

- A **non-ARM TigerJet** USB controller (DevType 1). Its register file is readable and writable with the
  `04 <reg> <reg&0xE0> <count> <data…>` framing. The ARM-style `00 00 <reg> 00` read returns the same bytes as
  little-endian 32-bit words, so the "ARM" register window used by `tj_linepower.py` is simply this chip's
  register file. Probe values: `reg 0x01 = 0x6c`, `reg 0x55 = 0x13`.
- The register file and datasheet match the **Tiger560B** family (`datasheets/Tiger560B.pdf`): vendor control, a
  4-wire SPI "serial μP" bridge at regs `0x26–0x29`, and AUX GPIO pins.
- **Analog line chip: not identified.** The repo assumes a Si321x ProSLIC, but on this unit the SLIC does not
  answer over the SPI bridge (see *SLIC / SPI bridge (Unit B)* below). Whether it is an SPI part wired differently or
  a different line interface is unknown.

## Register map (Unit B)  **[verified by observation; meanings partly inferred]**

Registers are bytes in the normal TigerJet space. The 32-bit "regs" used by `tj_linepower.py` are 4-byte
little-endian views of the same bytes (e.g. `reg0x38` = bytes `0x38–0x3b`).

| Byte(s) | Meaning on Unit B | Evidence |
|---|---|---|
| `0x00` | control (default `0x27`; the `tjctl.c` init sequence writes `0x50` then `0x51`) | dumps before/after `init` |
| `0x01` | `0x6c` — chip probe | `tj_slic.py tjdump` |
| `0x12` | **AUX pin input levels**; **bit 5 = hook** (1 = off-hook) | scope trace: `c7 → e7` on lift |
| `0x13` | AUX pin direction | `init` wrote `0x40`; AUX3/4/6/7 driven as outputs and read back in `0x12` |
| `0x15` | low nibble = **latched DTMF digit**, bit 6 = **digit strobe**, bit 7 normally set off-hook | scope trace |
| `0x08` bit 1 | high while a key is held (after ~100 ms) | wide scope |
| `0x09` bit 7, `0x58` bit 1 | change with hook state (set on lift, cleared on hang-up) | wide scope |
| `0x5f` | short pulse at the start and end of a held key | wide scope |
| `0x26–0x29` | SPI bridge data bytes + control (`0x29`: bit 0 start/busy, bit 5 pin enable, bit 7 3-byte) | datasheet + tests |
| `0x38` | codec/clock; `line_on()` writes `3` | write sticks |
| `0x55` | chip revision, `0x13` | probe |
| `0x08`, `0x0a`, `0x54`, `0x57`, `0x64` | fluctuate constantly when idle (counters / level meters) — ignore | idle-noise test |

DTMF digit codes in the nibble match the repo's table: `1–9` → themselves, `0xA` = `0`, `0xB` = `*`,
`0xC` = `#`. All of `1–9`, `0`, `*` and `#` were seen.

## Line power (Unit B)  **[partly verified]**

- `tj_linepower.py on` is accepted (bit 0 of reg 0 and `reg0x38` latch). With the handset lifted, **keypad
  tones are heard in the earpiece**, so the phone is getting loop current.
- **Not verified:** whether `line_on()` is required at all — the line may already be live after plug-in.
- Registers are **volatile and persist until unplug.** Experiments such as `tj_slic.py init` change reg `0x00` and
  AUX pins; **unplug and replug** to return to defaults. An early capture test returned pure silence on a unit
  that had not been replugged (and probably had the handset on-hook); capture worked after a replug with the
  handset off-hook.

## DTMF timing (Unit B)  **[verified — scope trace]**

- The **digit nibble updates the moment a key is pressed**, even for very short taps.
- The **strobe** (`0x15` bit 6) and `0x08` bit 1 only appear **~100 ms after the press**, and only while the key
  is still held (the strobe is ≈ 55 ms wide; `0x08` bit 1 stays up until release). The chip needs about 100 ms
  of tone before it flags it.
- The nibble **stays latched** after release, so **pressing the same digit again changes no quiet register
  byte.** Quick repeats of one digit are invisible to register polling.
- Consequence: register polling sees distinct digits immediately and held repeats, but not rapid same-digit taps.
  `mj-audio.py monitor --audio-dtmf` instead decodes DTMF from the captured audio (Goertzel, ~51 ms to confirm),
  independent of these registers. The detector was unit-tested on synthetic tones only; its thresholds are not
  tuned against many phones.

## Audio behaviour (Unit B)  **[verified unless noted]**

- Enumerates as an ALSA card `TigerJet` (USB-Audio). **Capture:** 8 kHz mono S16_LE only. **Playback:** 16 kHz
  (alt 1) or 8 kHz (alt 2) mono. Mixer: `PCM Playback Switch/Volume` (0–15, default 15) and
  `Headset Capture Switch/Volume` (0–15, default 8).
- **PulseAudio holds the playback side** (it opens it at 16 kHz), so direct `aplay -D plughw:N,0` fails with
  *Device or resource busy*. Use `pasuspender -- …` or play through Pulse. Capture is free.
- **Capture works** with the handset off-hook: a 1.46 kHz whistle was recorded cleanly. The firmware's **dial
  tone is not present in the capture**, and a tone played to the earpiece **does not leak into the capture**.
- **Dial tone:** heard during one run of `tj_audiotest.py` (handset lifted, capture open), but **not** with
  `mj-audio.py monitor`, and not when `--dialtone hw` merely held a capture stream open. The cause is
  **unresolved**. `mj-audio.py monitor` therefore plays the repo's `mj-fxs-dialtone.wav` itself at off-hook
  (`--dialtone file`, the default) and stops it at the first digit.

## SLIC / SPI bridge (Unit B)  **[verified negative result]**

- The TJ SPI engine runs: a transfer to regs `0x26–0x29` completes and `0x29` bit 0 clears. But every read of
  ProSLIC regs `0..0x6c` returned `0xff`.
- After replaying the `tjctl.c` init (AUX6 low/high, reset pulse via reg 0, SPI pin enable `0x29 = 0x20`) the
  result was unchanged. A sweep of **126 transactions** — each of AUX3/4/6/7 driven low and high, seven SPI
  control words, regs 0 and 1 — produced **no non-`0xff` reply**.
- The host therefore **cannot reach the line chip over SPI on this unit** with the known `tjctl.c` framing.

## Ringing (Unit B)  **[verified negative result]**

- `reg0` bits 8–9 (Unit A's ring request) and every single bit 8–15 were tried: the written values **do not
  latch** (readback unchanged) and the phone never rang.
- LINEFEED over SPI (the `tjctl.c` ring command) is unreachable because the SLIC doesn't answer.
- **Ring has not been found for Unit B.** The most promising route is a Windows USBPcap capture of the official
  driver ringing a phone; `protocol.md` notes the exact bit "needs a USBPcap diff".

## Open questions / leads

1. **Ring command** — needs a Windows USBPcap trace of the magicJack app ringing a phone.
2. **HID input reports** — hook and keypad events arrive on interrupt IN `0x85` (8-byte packets, 10 ms) and are
   exposed by the kernel via `hidraw`/`hiddev`. They might include short taps and give a cleaner event stream than
   register polling. Untested.
3. **Windows activation sequence** (`protocol.md`: regs `0x00`, `0x02`, `0x30–0x33`, `0x3c`, `0x55`, tone RAM
   `0x57`) targets this chip family. `tj_audiotest.py --activate` replays it; it was not needed for capture and
   its effect on dial tone / ringing is untested.
4. **Dial-tone source** — why it appeared in one test and not in `mj-audio.py monitor`.
5. **Which line chip is on the board** — open the case and read the markings.
6. **Firmware / flash work** (dump, config crypto, unpack) assumes the ARM CPU and does not apply to Unit B.
